# Security Decisions

## Purpose

[architecture.md](architecture.md) describes what the lab is built from. This document explains why the main decisions were made — the reasoning behind the configuration, not the configuration itself. It's meant to be read alongside the architecture document, not instead of it.

## Dedicated administrative account and key-only SSH

The lab uses `adminsec` as the only sudo administrator and the only account allowed to log in over SSH (`AllowUsers adminsec`). The original `ubuntu` account is no longer used for anything privileged. Separating "the account that administers the server" from "the default account the image shipped with" means privileged access is tied to one identifiable account instead of being spread across whatever happened to exist by default. It also makes administrative activity easier to pick out in logs and audit reports, since there's only one account it could be coming from. This is not a full privileged-access-management system on its own — there's no session recording or just-in-time elevation here — it's a starting point: know who your administrator is, and don't let anyone else be one.

SSH access for that account is key-only. The effective policy ([`configs/ssh/effective-ssh-policy.txt`](../configs/ssh/effective-ssh-policy.txt)) disables `PasswordAuthentication` and `KbdInteractiveAuthentication`, disables `PermitRootLogin`, and caps `MaxAuthTries` at 3. Password authentication over the network is guessable and phishable in a way a private key isn't — an attacker who wants in has to actually possess the key file, not just know or guess a string. The `adminsec` private key is stored on `sec-workstation` and is passphrase-protected, so even getting hold of the key file isn't enough by itself. `MaxAuthTries 3` limits how many attempts a single connection gets before it's dropped, which also keeps failed-authentication log noise down.

## Keeping the legacy `ubuntu` account instead of deleting it

`ubuntu` still exists on `sec-server`, but its previous access paths have been disabled: its password is locked, its old SSH key was removed from `authorized_keys`, it has no supplementary groups, and it's excluded from SSH entirely by `AllowUsers adminsec`. It wasn't deleted because deleting an account can leave files, cron history, and past audit log entries pointing at a UID that no longer resolves to anything — which makes later investigation more confusing, not less. Locking the account down while keeping the identity intact preserves that traceability while removing the access it used to have.

## Separating administration from auditing

The `auditor` account exists only to read generated audit reports. It's not a sudo user, and it can't log in over SSH at all, since `AllowUsers` only permits `adminsec`. Its read access comes from membership in the `security-auditors` group, which owns the report directory and files ([`generate-audit-report.sh`](../scripts/generate-audit-report.sh) sets the report directory to `root:security-auditors 0750` and each report file to `root:security-auditors 0640`). Nobody in that group can write to the reports — only root, via the script that generates them, can. The reasoning is simple: reviewing security output doesn't require the ability to change the system, or the reports themselves. Giving `auditor` anything more than read access would undermine the point of having a separate reviewing account. This is a small, lab-scale illustration of the idea, not a full enterprise separation-of-duties setup with independent approval workflows and the rest.

## Mutual TLS for centralized logging, and why encryption alone wasn't enough

Log traffic between `sec-workstation` and `sec-server` runs over TLS on TCP/6514. Earlier in the project this was encrypted but one-directional in terms of trust: the connection was private, but rsyslog on the server side wasn't checking who was actually sending the logs. Encryption alone stops an eavesdropper from reading the traffic, but it doesn't stop the wrong system — or nothing at all — from establishing the connection.

The lab moved to mutual TLS to close that gap. Both sides now hold certificates issued by a lab CA (`Security-Lab-CA`): a server certificate for `sec-server`, a client certificate for `sec-workstation`. `AuthMode x509/name` plus an explicit `PermittedPeer` on each side means each host checks the specific identity in the other's certificate, not just that it was signed by the right CA. See [architecture.md §5](architecture.md#5-centralized-logging-and-mtls-architecture) for the configuration details. The point of this section is just the reasoning: encryption protects the data in transit, authentication establishes who you're actually talking to, and this lab treats those as two separate problems that both needed solving.

## Certificate and key handling

Certificate and private key contents are intentionally excluded from this repository, and the lab CA's private key is never stored in it at all. What's published instead is the configuration that references those files, plus sanitized metadata about the certificates themselves (subject, issuer, SAN, key usage, file permissions — see [`configs/rsyslog/server-certificate-metadata.txt`](../configs/rsyslog/server-certificate-metadata.txt) and [`configs/rsyslog/workstation-certificate-metadata.txt`](../configs/rsyslog/workstation-certificate-metadata.txt)). That's enough to show how the mTLS setup works and to verify it against the running configuration, without putting actual key material on GitHub where it would be exposed indefinitely. Installed certificate and key files on both hosts use `root:syslog 0640` permissions, so only root and the `syslog` group can read them locally.

## Restricting TCP/6514 by source IP

UFW on `sec-server` allows TCP/6514 only from `192.168.223.128` — `sec-workstation`'s address (see [`configs/ufw/effective-ufw-policy.txt`](../configs/ufw/effective-ufw-policy.txt)). SSH is allowed separately and isn't restricted by source in the current policy. mTLS and the firewall rule address different things: mTLS checks *who* is connecting, at the application layer, by verifying a certificate identity. The firewall rule checks *where* the connection is coming from, at the network layer, before it ever reaches rsyslog. Neither replaces the other — a certificate check doesn't stop a connection attempt from reaching the port, and a source-IP rule doesn't verify identity. They're just two independent, fairly ordinary controls applied to the same service.

## Audit rule selection and immutable mode

`auditd` on `sec-server` doesn't try to log everything — it watches a specific set of security-relevant targets: identity files (`/etc/passwd`, `/etc/shadow`, etc.), sudo configuration, SSH configuration, the rsyslog/mTLS configuration and certificate directory, AppArmor configuration, the audit configuration itself, and privileged command execution (see [`configs/auditd/50-security-hardening.rules`](../configs/auditd/50-security-hardening.rules)). Auditing every filesystem event on a general-purpose system generates an enormous amount of noise and makes the log harder to actually use. Watching the files and actions that matter for this lab's threat model — who has access, how they authenticate, and what the logging/confinement/audit controls themselves look like — keeps the audit trail focused on things worth reviewing. The privileged-command rule is scoped by `auid`, the audit-subsystem's record of the *original* authenticated login, which stays attached to a process even after `sudo` changes its effective UID — so a command run via `sudo` still shows up tied to the person who logged in and escalated, not just to root.

The final rule file, [`99-finalize.rules`](../configs/auditd/99-finalize.rules), sets `-e 2`, and the verified runtime state confirms `enabled 2` ([`configs/auditd/effective-audit-state.txt`](../configs/auditd/effective-audit-state.txt)). This locks the audit configuration so it can't be changed while the system is running — modifying the rules requires a reboot. That's a deliberate tradeoff: it resists someone with root access quietly tampering with or disabling auditing at runtime, but it also means legitimate rule changes during testing or iteration are less convenient, since every change means a reboot to actually apply.

## AppArmor: extending the existing profile instead of replacing it

rsyslog on both hosts is confined by the Ubuntu-packaged AppArmor profile, left in enforce mode, with small local override files added on top ([`configs/apparmor/sec-server-rsyslog.local`](../configs/apparmor/sec-server-rsyslog.local), [`configs/apparmor/sec-workstation-rsyslog.local`](../configs/apparmor/sec-workstation-rsyslog.local)) that grant read access to exactly the certificate and key paths the mTLS setup needs. No custom rsyslog profile was written from scratch. The packaged profile is maintained upstream and already covers rsyslog's normal behavior reasonably well; replacing it entirely would mean taking on the job of tracking every path rsyslog legitimately needs, forever. Extending it with a narrow, well-understood addition gets the access that's actually missing without discarding that existing coverage.

## PAM password policy

Local accounts are subject to `pwquality` requirements: minimum length 14, at least one of each character class (upper, lower, digit, special) via the `*credit` settings, `minclass 3`, `maxrepeat 3`, `difok 4`, and `enforce_for_root` so root isn't exempt (see [`configs/pam/pwquality.conf`](../configs/pam/pwquality.conf)). SSH password authentication is disabled, so this doesn't protect the SSH path — it's there because local password quality still matters for console access, `sudo` prompts, and simply demonstrating that the control is understood and correctly wired into the PAM stack. These rules reject several common forms of weak passwords, but they do not guarantee that an accepted password is strong — a password can satisfy every rule here and still be predictable. This is one layer, not a complete answer to authentication security by itself.

## PAM faillock and Fail2Ban: two layers, not one

`pam_faillock` (`deny 5`, `fail_interval 900`, `unlock_time 300` — [`configs/pam/faillock.conf`](../configs/pam/faillock.conf)) and the Fail2Ban `sshd` jail (`maxretry 5`, `findtime 600`, `bantime 600` — [`configs/fail2ban/effective-sshd-jail.txt`](../configs/fail2ban/effective-sshd-jail.txt)) look similar but operate at different layers. `pam_faillock` protects the authentication mechanism itself — it locks the *account* after repeated failures, regardless of where the attempt came from. Fail2Ban watches the SSH service's logs and reacts to repeated failures from a given *network source* by blocking that source at the firewall level for a period of time. One is account-centric, the other is network-source-centric, and together they cover a case neither handles alone: faillock doesn't block the network path, and Fail2Ban doesn't touch the account state. Note that this project doesn't claim any of the failed-login activity observed during testing represents real attack traffic, and the values above are the effective `sshd` jail configuration observed on `sec-server` — the lab doesn't ship a custom `jail.local`.

## No fixed password-expiration policy

The lab does not enforce a fixed password rotation schedule (e.g., forcing a change every 90 days). This is a deliberate choice for this project, not a claim about what every organization should do: forcing periodic changes without another underlying reason tends to push people toward small, predictable password variations, which doesn't necessarily improve security. Instead, this lab leans on password quality rules, account restrictions, key-based SSH, and lockout controls to cover the same underlying concerns.

## Automation and retention

Four scripts run on a schedule via cron rather than being run by hand: [`monitor-system.sh`](../scripts/monitor-system.sh) every 5 minutes, [`generate-audit-report.sh`](../scripts/generate-audit-report.sh) daily, [`backup-security-logs.sh`](../scripts/backup-security-logs.sh) daily, and [`cleanup-backups.sh`](../scripts/cleanup-backups.sh) weekly (see [`configs/cron/root-crontab`](../configs/cron/root-crontab)). Manual execution of monitoring or backup tasks is easy to forget or skip, especially something that's supposed to happen every few minutes or every day — automating it means the tasks actually happen consistently instead of depending on someone remembering. Audit reports and backups are both retained for 30 days before being cleaned up, and the automation logs themselves are rotated by logrotate ([`configs/logrotate/security-hardening`](../configs/logrotate/security-hardening)) so they don't grow indefinitely. The 30-day figure is a lab design choice made to keep enough history to be useful without keeping everything forever — it isn't derived from any specific compliance requirement.

## What I Learned

Working through this lab made it clear that Linux hardening isn't one setting you flip — it's a handful of controls that each cover a different, narrower problem, and the security of the system comes from how they fit together rather than from any single one of them. SSH key-only auth, faillock, Fail2Ban, mTLS, and the firewall rule for port 6514 all look like they overlap on the surface, but each one is actually answering a slightly different question, and I had to think through what each was and wasn't covering.

The other big lesson was that configuration doesn't mean much until you've checked what the system is actually doing with it. A few of the files in this repository exist specifically because I went and verified effective state — `sshd -T`, `auditctl -s`, UFW's status output, Fail2Ban's jail state — instead of assuming the config file I wrote was the whole story. More than once what I expected and what was actually running weren't quite the same thing, and that gap is exactly what's worth documenting.

Finally, I came away with a clearer sense of where the edges of this project are. Encryption and authentication solve different problems even when they show up in the same TLS handshake. Permissions and account design (who can log in, who's in which group, who owns what) matter as much as any individual daemon's configuration. And writing down what this lab doesn't do — no certificate rotation, no IPv6 coverage for the logging port, a Fail2Ban jail I didn't customize — felt more useful than only listing what it does. I don't have production experience running any of this at scale, and this document isn't meant to suggest otherwise; it's a record of what I built, tested, and understood well enough to explain.
